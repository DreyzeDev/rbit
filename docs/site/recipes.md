# Рецепты

Практические сценарии работы с rbit. Все примеры рассчитаны на установленный пакет
(`pip install -e .`) и выполняются из корня проекта.

## 1. Починить падающий тест

Самый частый сценарий: тесты красные — пусть агент разбирается.

1. Сначала посмотрите на падение сами, чтобы в промпте назвать конкретный тест:

    ```bash
    pytest -q
    ```

2. Попросите агента починить его, прямо в TUI:

    ```text
    tests/test_app.py::test_checkpoints падает. Найди причину и исправь код,
    но не правь сам тест, если он проверяет ожидаемое поведение.
    ```

3. Проверьте результат мгновенным шеллом без траты токенов:

    ```text
    !pytest -q tests/test_app.py
    ```

Для headless-исполнения (например, в скрипте) то же самое делает CLI:

```bash
rbit run "почини падающий тест tests/test_app.py::test_checkpoints" --output-format json
```

!!! tip
    Агент делает авто-чекпоинт перед правками, поэтому откат — это `/rewind`,
    даже если проект не под Git.

## 2. Ревью диффа через `@diff`

Перед коммитом полезно взглянуть на изменения глазами второй пары — виртуальные
аттачи кладут diff прямо в контекст, без чтения файлов агентом.

1. Сделайте изменения и посмотрите сводку:

    ```text
    /diff
    ```

2. Запросите ревью по текущему диффу:

    ```text
    @diff просмотри изменения: найди баги, утечки ресурсов и пропущенные edge-case'ы.
    Предложи конкретные правки, но ничего не меняй.
    ```

3. Если ревьюить нужно уже подготовленное (staged), берите `@staged`, а для общего
   состояния ветки — `@git`.

4. После правок попросите черновик сообщения коммита:

    ```text
    /commit
    ```

!!! note
    Режим *Plan* (`Tab`) не даёт агенту менять файлы — удобно именно для ревью.

## 3. Своя слэш-команда

Повторяющиеся промпты удобно превратить в команду проекта: один Markdown-файл в
`.rbit/commands/` — и она появляется в палитре с автодополнением.

1. Создайте `.rbit/commands/review.md`:

    ```markdown
    Просмотри {args} как код-ревьюер: баги, стиль, edge-case'ы.
    Ничего не правь, перечисли проблемы по убыванию важности.
    ```

2. Вызовите её в сессии:

    ```text
    /review src/app.py
    ```

3. `{args}` подставляется из аргументов команды, так что один шаблон работает для
   любого файла или каталога.

Команды лежат в проекте и попадают в репозиторий — вся команда получает одинаковый
ревью-промпт.

## 4. Чекпоинты для рискованного рефакторинга

Крупное переименование или перестройка модуля — как раз случай, когда нужен
надёжный «машина времени», работающий даже вне Git-репозитория.

1. Зафиксируйте точку возврата с говорящим именем:

    ```text
    /checkpoint before-storage-refactor
    ```

2. Запустите рефакторинг и проверяйте тесты по ходу мгновенным шеллом:

    ```text
    !pytest -q
    ```

3. Если что-то пошло не так — откатитесь к снимку:

    ```text
    /rewind
    ```

4. Точечные правки откатываются и без чекпоинтов: `/undo` отменяет последнее
   изменение файлов, `/redo` возвращает его.

!!! warning
    Чекпоинты хранятся в `.rbit/checkpoints/` с ротацией (последние 20), поэтому
    не стоит коммитить эту папку — она уже в `.gitignore`.

## 5. Автоматизация в CI через `rbit run`

Headless-режим — способ использовать агента в пайплайнах: без TUI, с машиночитаемым
выводом и понятным кодом возврата.

1. Базовый шаг в GitHub Actions:

    ```yaml
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: "3.12"
    - run: pip install .
    - name: rbit fix warnings
      env:
        RBIT_API_KEY: ${{ secrets.RBIT_API_KEY }}
      run: |
        rbit run "исправь предупреждения ruff в rbit/" --output-format jsonl \
          | tee rbit-output.jsonl
    - uses: actions/upload-artifact@v4
      if: always()
      with:
        name: rbit-output
        path: rbit-output.jsonl
    ```

2. Ключ провайдера передаётся переменной окружения (`RBIT_API_KEY`,
   `OPENROUTER_API_KEY` или `OPENAI_API_KEY`) — без неё агент вернётся к локальному
   Smart-агенту.

3. Для строгой проверки вместо правок используйте read-only запрос и проверку кода
   возврата:

    ```bash
    rbit lint --json          # exit 1, если есть ошибки
    rbit map --json           # карта проекта и бюджет токенов
    ```

4. Событийный поток `--output-format jsonl` (`tool_call` / `message` / `done`)
   удобно парсить в шаге-постобработке или складывать в артефакт как журнал
   действий агента.

В репозитории есть готовый composite action `.github/action.yml` — шаблон шага
«установить rbit, выполнить задачу, сохранить jsonl» для переиспользования.
